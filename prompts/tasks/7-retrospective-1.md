# Codebase Review Prompt — Tech Debt Audit

Copy everything below into Claude Code in the root of the repo.

---

You are conducting an exhaustive, file-by-file technical audit of this Python
codebase. Your job is to find structural problems, tech debt, anti-patterns,
and test coverage gaps, then write the findings to `tech-debt.md`. This is a
read-only audit — do not fix anything, do not refactor anything, do not
modify any file other than `tech-debt.md` itself.

## Scope

- Review the entire repository.
- Read every Python source file, not just the obvious entry points. Skip
  only: virtual environments, `__pycache__`, build artifacts, vendored/
  third-party code, and generated files (e.g. migrations auto-generated by a
  framework, protobuf/grpc generated code). If you're unsure whether
  something is generated/vendored, ask me before skipping it.
- Include config files, build scripts, and CI config if present, but only
  flag issues in them that relate to code structure/tech debt (not style
  nitpicks).

## What to look for

**1. Code structure**
- Module/package organization — does it reflect a coherent architecture, or
  has it grown organically without a plan?
- Circular imports or tight coupling between modules that should be
  independent.
- Misplaced responsibilities (e.g. business logic in views/routes, DB
  queries scattered outside a data layer, config hardcoded deep in
  unrelated modules).
- Inconsistent patterns for the same kind of problem solved differently in
  different places (e.g. three different ways of making HTTP calls).

**2. Tech debt**
- Dead code (unused functions, classes, imports, commented-out blocks left
  in place).
- Duplicated logic that should be extracted/shared.
- TODO/FIXME/HACK comments — catalog them, don't just count them.
- Outdated or deprecated library usage; dependencies pinned in ways that
  block upgrades.
- Inconsistent error handling (bare `except:`, swallowed exceptions, mixed
  use of exceptions vs. error-return-codes).
- Inconsistent or missing type hints in a codebase that otherwise uses them
  (or vice versa — partial adoption left half-finished).
- Configuration/secrets handling smells (hardcoded values that should be
  env vars, etc.) — flag but do not print actual secret values if any are
  found in plaintext; just flag the file/line and the risk.

**3. Anti-patterns**
- God objects/functions (classes or functions doing too much).
- Deep nesting / high cyclomatic complexity.
- Mutable default arguments, global mutable state, singleton misuse.
- Overuse of `*args`/`**kwargs` that obscures real interfaces.
- Leaky abstractions (e.g. ORM objects passed directly through every layer
  up to the API response).
- Premature or unnecessary abstraction (overengineering for flexibility
  that's never used).

**4. Test coverage gaps**
- Identify modules/functions with no corresponding tests.
- Identify tests that exist but are weak (e.g. only happy-path, no edge
  cases, no error-condition tests, tests that mock so much they don't test
  real behavior).
- Note any test infrastructure issues (flaky-looking tests, skipped tests
  left skipped, no CI gate on tests if that's discoverable from config).
- If there's a coverage tool already configured in the repo, use it to get
  actual numbers. If not, estimate coverage qualitatively per module rather
  than guessing a precise percentage.

## How to work

- Go file by file. Don't sample — this is an exhaustive review, so read
  everything in scope.
- As you go, keep a running list of findings rather than trying to
  remember everything for the end.
- If the repo is large enough that full exhaustive reading risks running
  out of context, stop and tell me before continuing — don't silently
  switch to a lighter sampling pass.
- If you find something ambiguous (e.g. you're not sure if a pattern is
  intentional or accidental, or you're not sure if a directory is in scope),
  ask me rather than assuming.

## Output: `tech-debt.md`

Write all findings to a single file `tech-debt.md` at folder `prompts/tasks`, with
this structure:

```markdown
# Tech Debt Audit — <repo name> — <date>

## Summary
- One paragraph: overall health of the codebase.
- Counts: total findings by severity (High/Med/Low).
- Top 5 issues that matter most, in priority order.

## Findings

For each finding:

### [SEVERITY] Short title
- **Location:** file path(s) and line numbers
- **Category:** structure | tech-debt | anti-pattern | test-gap
- **Description:** what's wrong, in plain language
- **Why it matters:** concrete consequence (bug risk, onboarding cost,
  perf, security, etc.) — not just "it's bad practice"
- **Suggested fix:** brief, directional, not a full implementation
- **Effort estimate:** S / M / L
  - S = under a day
  - M = a few days
  - L = needs planning/design, multi-week or cross-team

(Repeat for every finding, grouped by severity: all High first, then
Medium, then Low.)

## Test coverage summary
- Table or list of modules with notably low/no coverage.
- Pattern-level notes on test quality (not file-by-file unless notable).

## Open questions
- Anything you were unsure about and skipped or need my input on.
```

Severity definitions:
- **High** — actively causing or likely to cause bugs, security exposure,
  or is actively blocking changes/scaling.
- **Medium** — not urgent but compounding (will get worse / more
  expensive the longer it's left).
- **Low** — cosmetic or minor inconsistency, fine to defer indefinitely.

## Before you start

If anything about scope, depth, or the project's intended architecture is
unclear to you, ask me first. Do not assume conventions, intended patterns,
or priorities — ask rather than guess.
